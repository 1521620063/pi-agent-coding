# PI VS Code 侧边栏桥接插件设计

日期：2026-11-11

状态：已按用户要求纳入推荐集成功能，供后续开发；本文不代表实现已经完成。

## 1. 意图与已确认边界

用户希望在 VS Code 侧边栏中使用电脑上已经安装的 PI，无需打开终端。聊天、执行过程和会话操作的使用方式参考 Codex、Claude Code 的 VS Code 插件；界面的样式风格尽量参考 PI 本身，以 PI 为视觉设计的主要依据。

插件负责图形界面和编辑器集成。推理、工具调用、文件修改、模型接入及会话内容继续由本机 PI 负责。PI 没有提供的智能体能力，不由插件另行实现。

已确认的环境：仓库目前只有 README 和 LICENSE；开发机为 Windows；通过本机 `pi --version` 确认已安装 PI 1.5.2；其安装包提供 RPC 文档、协议类型及工具源码。1.5.2 是本机验证基线，不代表所有 PI 版本都兼容。

用户已要求将可集成且推荐的能力写入开发计划，稍后按计划开发。本文与配套的 [实施计划](../plans/2026-11-11-pi-vscode-bridge-plan.md) 一起定义开发范围；技术选型和阶段划分是作者建议，本次只更新文档。

## 2. 方案取舍

| 方案 | 优点 | 代价与适用性 |
| --- | --- | --- |
| **启动用户安装的 PI，通过 RPC 交互（采用）** | 使用正式的 IDE 接口；延续用户现有 PI 安装、配置和会话；扩展与 PI 进程隔离 | 只能使用 RPC 暴露的能力；需要处理进程生命周期和协议差异 |
| 嵌入 PI SDK | 直接使用完整的程序接口 | 将 PI 运行库带进插件并承担版本和依赖管理，不符合本项目只桥接本机 PI 的边界 |
| 将终端界面嵌入侧栏 | 可保留终端操作习惯 | 无法提供期望的原生聊天侧栏体验，也缺少可靠的结构化交互边界 |

基于用户强调的能力边界，只采用第一种。无须安装插件自带的 PI、修改用户的 PI 安装或注入新的 PI 扩展。

## 3. 首版用户体验

这是一个独立的 VS Code 扩展项目。活动栏提供 PI 入口，侧栏内从上到下安排会话操作、对话时间线和输入区。采用 PI 的简洁、文本优先的界面风格，结合 VS Code 当前主题和字体适配窄侧栏，具体约束见 3.8。

### 3.1 连接与初次使用

- 用户打开可信的本地工作区后，打开 PI 侧栏即可连接本机 PI。
- 自动寻找 PATH 中的 `pi`，兼顾官方安装器的常用位置；也允许在 VS Code 设置中指定可执行文件路径。
- 使用所选工作区目录启动 `pi --mode rpc`，继承用户环境与 PI 默认配置。默认不覆盖模型、工具、技能或会话目录。
- 无工作区时提示打开文件夹；多根工作区需要选择本轮使用的目录。更换目录之前停止活动任务并关闭当前子进程。
- 没有找到 PI、Node 不可用、配置或登录异常时，在侧栏显示具体原因和修复入口。插件不安装 PI，也不收集或保存供应商凭证。
- 首版仅承诺本地 VS Code 扩展宿主。WSL、SSH、容器和浏览器版 VS Code 暂不列为支持环境，避免把远程宿主的 PI 混同于用户电脑上的 PI。

### 3.2 聊天与执行

- 输入框支持多行输入、发送、停止；发送后展示用户消息及 PI 的流式回复。
- 回复支持 Markdown 和代码块。仅在 PI 返回思考内容时显示可折叠思考区，不生成或推测缺失内容。
- 工具调用以卡片展示名称、参数摘要、运行状态和结果；长输出可折叠，错误可展开。
- 模型正在运行时，用户可以选择把新消息追加到后续队列，或通过 PI 的 steer 能力追加指示。界面区分排队与正在执行。
- steer 在当前助手轮次的工具执行结束后、下一次模型调用前交付，不承诺打断正在执行的工具。队列以 PI 的 `queue_update` 事件为准；“全部停止”先 `clear_queue` 再 `abort`，防止取消当前轮次后继续执行排队任务。
- 支持将当前选区或用户明确选择的文件作为消息上下文附加，发送前可查看和移除。由扩展宿主读取已选择的内容，不后台收集整个工程；作为普通文本提交给 PI。
- 支持粘贴、选择或拖入图片，发送前显示可移除的缩略图。图片通过 RPC 的 `images` 字段发送，仅在 PI 返回的当前模型输入能力包含 image 时启用；不把图片转成伪文本附件。
- 错误消息提供适当的重试操作。PI 崩溃或连接丢失后，不自动重放可能执行工具的用户消息。

### 3.3 会话与设置

- 支持新建会话，保留 PI 自身生成的会话文件。
- 会话列表展示插件曾打开或创建的 PI 会话。用户也可通过文件选择器打开已有 PI `session.jsonl`，交由 PI 的 `switch_session` 加载。
- 首版不承诺自动枚举所有终端历史会话，因为已核对的 RPC 命令中没有 `list_sessions`。插件仅保存工作区到会话路径的轻量索引，不另建一套聊天记录数据库，不改写 PI 会话文件。
- 恢复会话后，通过 PI 返回的消息重建当前分支；不直接把整个 JSONL 当成线性对话读取。
- 模型菜单使用 PI 返回的可用模型；思考强度菜单使用 PI 返回的可用选项。插件不维护自己的供应商或模型清单。
- 首版提供当前工作区最近会话恢复入口，不默认强制切回用户终端中最近使用的会话。
- 支持会话重命名；后续增强阶段支持复制当前会话、从当前分支的历史用户消息创建分叉、只读查看会话树和导出 HTML。
- 分叉改变对话上下文，不回滚文件。`get_tree` 只用于浏览，不据此承诺 RPC 没有暴露的任意节点导航。

### 3.4 文件变更和确认交互

- 本机 PI 1.5.2 的内置 `edit` 工具写入成功后，在工具结果 details 中返回差异信息。插件可在该工具卡片中显示这份**已发生修改的差异**，并提供打开文件的操作。
- 这不是修改之前的预览，也不等于所有工具都返回完整差异。`write`、命令行或自定义工具没有提供差异时，仅展示它们实际返回的结果。
- 首版不创建变更审批引擎、文件快照、自动回滚或逐块接受/拒绝功能。不得将“接受”按钮做成文件实际已被修改后的装饰性确认。
- 用户现有 PI 扩展通过 RPC 发出 `confirm`、`select`、`input` 或 `editor` 请求时，插件展示对应控件，并把回答或取消结果原样送回 PI。
- 上述确认是既有 PI 扩展提供的能力，不意味着 PI 默认会对每次写文件或运行命令发起确认。依赖 TUI 的自定义界面不在支持范围内。

### 3.5 技能、模板与已有 MCP 能力

- 输入 `/` 时展示 `get_commands` 返回的扩展命令、提示词模板和技能；通过 `prompt` 原样提交所选命令，不复制 PI 的模板展开或技能加载逻辑。
- 用户已有的 PI 扩展、技能、MCP 服务、自定义供应商和本地模型继续由 PI 自身加载。插件不加 `--no-extensions`、`--no-mcp` 等禁用参数，不接管资源发现、MCP 连接或鉴权。
- MCP 和自定义工具使用通用工具卡片，不假设工具名只有 read、edit、write、bash；资源内容按 PI 实际返回的文本、图片或其他结构展示。
- 这是已有能力的使用与展示，不包括安装/卸载技能、包、MCP 服务器管理面板或供应商登录界面。相关 CLI 命令不等同于已有 RPC 管理接口。

### 3.6 上下文、用量与重试

- 展示 `get_session_stats` 提供的上下文占用、输入/输出 Token、缓存 Token 和费用统计。不将统计费用称为实际账单，也不自行推算服务商剩余额度。
- 支持手动压缩上下文、可选压缩指示、自动压缩开关，以及压缩进度和完成摘要。
- 未返回用量时显示不可用；压缩后的占用暂为 null 时显示等待更新，不显示为零或沿用旧百分比。
- 显示 PI 自动重试的原因、次数和等待状态，提供启用/禁用以及取消重试操作；插件不再叠加自己的模型请求重试循环。
- 后续增强阶段可以提供独立的命令执行面板，通过 `bash` / `abort_bash` 调用 PI 执行器，支持取消和结果是否加入后续模型上下文的选择。该面板默认收起，不替代聊天输入；Windows 的实际 shell 行为需单独验收。

### 3.7 开发阶段

| 阶段 | 范围 | 可交付结果 |
| --- | --- | --- |
| P0：可用闭环 | 进程与 RPC、侧栏聊天、停止、工具卡片、基本差异、文件/选区/图片、模型与思考强度、技能/模板命令、基本会话与命名 | 能在 Windows 本机 VS Code 中完成真实 PI 对话和工具任务 |
| P1：推荐日常功能 | 消息队列可视化、用量、上下文压缩、自动重试控制 | 达到日常工作可用；是推荐的首个发布范围 |
| P2：后续增强 | 会话复制/分叉/只读树/HTML 导出、完整扩展交互及状态组件、独立命令面板 | 在已有闭环上扩充高级操作 |

基础扩展确认/选择/输入在 P0 即需可响应或明确取消，不能让已有 PI 扩展无限等待；P2 再补齐丰富展示。MCP、自定义工具和模型的默认继承从 P0 起生效。全部能力都纳入计划，P0、P1、P2 是开发顺序，不表示 P2 已完成。

### 3.8 视觉规范：以 PI 本身为主要参考

此要求来自用户的明确补充。Codex / Claude Code 只作为侧栏交互组织的参考；布局细节、消息呈现、配色语义和信息密度优先参考本机 PI 1.5.2 的交互界面。

参考依据为 PI 的 `docs/themes.md`、内置 `dark.json` / `light.json` 及 user-message、assistant-message、tool-execution、footer 组件。PI 默认 system 主题随终端配色适应，因此“像 PI”不等于始终使用同一套固定深色或固定紫色。

| 区域 | 视觉要求 |
| --- | --- |
| 整体 | 紧凑、文本优先、平面化；使用细分隔线和留白建立层次。装饰保持克制，避免渐变、大面积品牌色、重阴影、头像列和大圆角聊天气泡 |
| 用户消息 | 参考 PI 的 userMessageBg / userMessageText，使用轻微蓝调的整行浅底色块，内容与对话正文共用左对齐基线 |
| 助手回复 | 连续 Markdown 正文，背景融入侧栏；代码块和引用按内容需要区分，不为整段回复再嵌套一层装饰卡片 |
| 思考内容 | 参考 thinkingText，以次要文字和轻量展开入口呈现，正文始终是主要阅读层级 |
| 工具结果 | 紧凑的平面区块，工具名称与摘要在上、输出在下；参考 toolPendingBg / toolSuccessBg / toolErrorBg 的中性、绿、红语义，用文字状态与颜色共同表达进度和结果 |
| 输入区 | 固定在底部的多行编辑区，以细边界和焦点状态区分；模型、思考强度和附件操作紧邻输入区，避免大型按钮占用正文空间 |
| 状态信息 | 参考 PI footer，将工作目录、模型、思考强度、上下文和 Token 放入低干扰的紧凑状态行；窄宽度可分行，完整信息可查看 |
| 差异与代码 | 沿用 PI toolDiffAdded / toolDiffRemoved / toolDiffContext 的增绿、删红、上下文弱化语义；命令、路径、代码与日志使用编辑器等宽字体 |
| 主题和可达性 | 明暗、高对比度与键盘焦点均可用；正文、工具输出和状态文字保持可读。PI 配色语义与宿主对比度冲突时，优先保证可读性 |

实施时新增独立 `webview/theme.css`，用 `--pi-*` 语义变量集中表达 accent、text、muted、userMessage、toolPending/Success/Error、thinking、diff、border 等角色。借鉴 PI system 的适应方式，将这些角色映射到 VS Code 的编辑器、侧栏和终端 ANSI 颜色；内置 dark/light 主题用于对照与缺失色值的参考。不要把 OKHSL 源值直接当成浏览器 CSS；需要借用具体色值时先转换为支持的 CSS 表示并校验对比度。

视觉适配不导入 PI TUI 运行库、不模拟终端字符边框、不修改 PI 主题配置，也不承诺通过 RPC 读取或同步用户当前自定义主题。后续若需要精确导入自定义主题，应另行定义主题适配功能。

验收需将用户消息、助手 Markdown、折叠思考、工具运行/成功/失败、输入区和底部状态，与 PI 自身对应区域逐项对照。在 VS Code 明暗、高对比度、320px / 480px 侧栏和 200% 缩放下保留对照截图与结果，不能只因功能正常就标记视觉验收通过。

## 4. 能力映射

| 界面能力 | PI 来源 | 边界 |
| --- | --- | --- |
| 流式聊天 | `prompt`、`message_start/update/end` | 模型实际返回的内容 |
| 停止、补充指示、排队 | `abort`、`steer`、`follow_up`、`clear_queue` | 以 PI 确认的处理状态为准 |
| 工具卡片 | `tool_execution_start/update/end` | 不把展示层事件当作执行前拦截点 |
| 新建和打开会话 | `new_session`、`switch_session`、`get_messages`、`get_state` | 历史索引范围见 3.3 |
| 模型与思考强度 | `get_available_models`、`set_model`、`get_available_thinking_levels`、`set_thinking_level` | 实际选项由 PI 和模型决定 |
| 用量信息 | `get_session_stats` | 仅展示 PI 提供的统计，不独立估算账单 |
| 编辑差异 | 内置 `edit` 工具的结果 details | 修改完成后的展示；缺失则不展示 |
| 确认、选择、补充输入 | `extension_ui_request/response` | 仅响应 PI 发出的请求 |
| 自定义斜杠命令 | `get_commands`，经 `prompt` 提交 | 可发现的扩展命令、模板、技能；不模拟 TUI 命令 |
| 图片附件 | `prompt.images` 与模型 `input` | 仅用于支持图片的模型 |
| 上下文压缩 | `compact`、`set_auto_compaction`、`compaction_start/end` | null 占用和估算值按原语义展示 |
| 自动重试 | `set_auto_retry`、`abort_retry`、`auto_retry_start/end` | 重试由 PI 执行 |
| 会话命名、复制、分叉 | `set_session_name`、`clone`、`fork`、`get_fork_messages` | 分叉不恢复文件 |
| 树形历史与导出 | `get_tree`、`get_entries`、`export_html` | 树只读；导出到用户选择的位置 |
| 扩展状态与通知 | `notify`、`setStatus`、`setWidget`、`setTitle`、`set_editor_text` | widget 只支持 RPC 文本行 |
| 独立命令面板 | `bash`、`abort_bash`、`bash_execution_update` | 输出在后续 prompt 才进入模型上下文；可排除 |
| 已有 MCP 与自定义资源 | PI 默认资源加载和通用工具事件 | 不提供没有 RPC 支持的连接管理接口 |

`/settings`、`/hotkeys` 等仅面向 TUI 的内置命令不能直接当成 RPC 命令发送。首版的模型、思考强度和会话操作使用各自正式 RPC 接口。自定义斜杠命令只展示 PI 返回的可发现项。

## 5. 技术结构

建议使用 TypeScript、VS Code Extension API、esbuild，以及轻量的 TypeScript Webview。首版无需 React 或额外服务端。具体构建文件划分可由实施者决定。

```text
侧边栏 Webview
    │ 受校验的消息 / 可序列化视图状态
VS Code 扩展宿主
    ├─ 侧栏提供器、编辑器上下文、工作区会话索引
    └─ PI 进程控制器 / JSONL RPC 传输与状态归并
            │ stdin / stdout；stderr 单独处理
        用户已安装的 PI --mode rpc
            └─ PI 原有模型、工具、技能、配置与会话存储
```

扩展不导入 PI 的智能体运行库，不直接调用模型 API。Webview 不直接访问文件系统、创建进程或连接供应商。

### 5.1 进程控制

- 每个 VS Code 窗口首版只维护一个当前工作区 PI 进程；隐藏侧栏不停止已有任务。
- 本机 PI 路径、启动参数使用结构化参数传递，不拼接用户文本为 shell 命令。Windows 需明确处理 `.cmd` / `.ps1` 启动器与 Node 入口，不能假设 Unix 可执行文件规则通用。
- 对托管安装，只通过其官方启动器解析当前安装，不将本机 1.5.2 的绝对安装路径写进产品。
- 关闭工作区、重载扩展或退出时，关闭 stdin 请求有序退出，设置有限等待后清理由插件创建的进程树。Windows 启动器和它产生的实际 PI 进程均需纳入生命周期管理。
- 取消、会话切换、进程退出均应结束相应 UI 等待状态，并处理悬挂的 RPC 请求及扩展交互请求。
- stderr 写入可查看的 PI 输出通道；不记录完整环境变量、凭证或原始敏感配置。

### 5.2 协议与状态

- stdout 按 UTF-8 字节流解码并仅以 LF 分割 JSONL，兼容 CRLF。处理半个 UTF-8 字符、跨块记录、多条记录合并及 JSON 字符串中的 U+2028/U+2029。
- 每条请求使用唯一 ID，与响应对应；响应顺序不可用于关联请求。持续消费 stdout，处理输入背压。
- 在发送 prompt 之前安装事件监听。成功的 prompt 响应只表示接收情况；依据 disposition 区分 started、queued 或 handled。
- 本机 1.5.2 使用 `agent_settled` 判断自动后续工作全部结束；`agent_end` 不能直接代表本轮交互最终完成。
- 扩展宿主维护连接、会话、运行、队列和待交互状态。Webview 重新加载时重新获取完整视图状态，不能丢失仍在运行的任务。
- 对当前协议先做本机 1.5.2 的实际握手验证。未知命令失败或字段不兼容时说明兼容性问题，不无声假定旧版可用。更老版本只有在实际验证后才扩大支持范围。
- 控制消息具有合理的超时；模型执行过程没有简单套用短 RPC 超时。超长输出分批渲染并限制默认展开量，保留运行结束和错误等关键状态。

### 5.3 Webview 和工作区边界

- 使用 VS Code 主题变量，支持键盘操作、可读焦点状态和输入法组合输入；Enter 发送时不打断中文输入。
- Markdown 禁用原始 HTML 和可执行内容；外部链接经明确的安全路径打开。设置 CSP，资源限定为扩展自身的必要文件。
- 宿主校验来自 Webview 的消息类型和参数。会话文件、文件内容、工具输出一律作为数据处理。
- 未受信任工作区不启动 PI。打开已有会话使用宿主文件选择器；索引中的会话路径不能由 Webview 任意改写。

## 6. 不在首版范围

- 插件内置、自动下载或更新 PI，供应商登录管理与密钥管理。
- 重写智能体循环、工具执行、沙箱或权限策略。
- 原生 PI RPC 未提供的逐项变更审批、任意执行的撤销，以及全量终端界面兼容。
- 自动扫描所有 PI 历史、跨设备同步、并行多智能体、多会话同时执行。
- 自动生成或注入新的 PI 扩展来补充功能。
- 技能、包或 MCP 服务器的安装管理界面，以及插件自行实现的计划模式、多智能体编排。
- 移动端、远程扩展宿主和 VS Code Web。

交互组织可以参考其他插件，视觉优先参考 PI 自身，但不承诺与其他插件所有功能等同。README 与实际桥接范围保持一致，不宣传原生接口未提供的变更审批。

## 7. 验收与验证

1. 在本机已安装 PI 的前提下，以扩展开发模式打开仓库，侧栏能检测版本并启动工作区中的 RPC 会话，全程无需打开终端。
2. 真实 PI 的状态、模型、思考强度、会话读取等低成本控制命令可正常工作；一个明确发送的真实聊天请求能流式显示并可停止。真实模型测试使用用户现有 PI 凭证，产生的调用应单独记录，不能把模拟传输测试当成真实模型验证。
3. 模拟进程测试覆盖消息分片、UTF-8、多请求乱序、排队、`handled`、自动重试后 settled、停止和异常退出，证明界面不会提前结束或永久卡住。
4. 新建、切换、恢复会话正确，切换被 PI 扩展取消时保持旧会话；Webview 重载后任务与消息仍可恢复。
5. 工具卡片正确展示成功、错误及部分输出。只有 PI 提供差异时才渲染差异，并明确已经执行；界面没有虚假的接受或拒绝修改功能。
6. PI 已有扩展的确认、选择、输入、取消及超时正常完成，不支持的终端 UI 功能清晰说明。
7. 未安装 PI、无工作区、不可信工作区、中文输入、窄侧栏、明暗主题及进程退出可验证；Windows 关闭扩展后不遗留插件创建的 PI 进程。
8. 编译、针对桥接风险的单元测试与 VSIX 打包通过。Windows 是首个实际验证平台；macOS、Linux 仅在实际验证后声明支持。
9. 图片能力随模型切换启用/禁用；命令菜单仅来自 `get_commands`。已有 MCP 和未知工具名不导致渲染崩溃。
10. 压缩和重试状态正确，缺失或暂为 null 的统计不显示虚假数字；“全部停止”后队列为空且不会继续运行。
11. 分叉/复制不改变文件，树浏览不擅自切换分支；导出和命令面板分别处理取消、失败及截断输出。
12. 界面按 3.8 参考 PI 自身完成视觉对照，具备明暗/高对比度和窄侧栏截图记录；没有将聊天呈现做成其他插件品牌风格的复制。

## 8. 留给实施者的选择

可以自主确定模块命名、DOM 渲染细节、构建脚本、测试工具、事件合并频率、超时和显示上限，以及不改变上述边界的交互微调。先以真实 RPC 握手和可取消的最小聊天闭环验证桥接，再补足会话、工具展示及界面细节。

如果发现必须嵌入 SDK、修改用户 PI 安装、注入自定义 PI 扩展或实现新的执行策略才能满足某项需求，需重新确认设计，不得将其当作普通实现细节。
